# Инструкции для учебного проекта: Cursor, Claude Code и Codex

## Перед каждой задачей

Прочитай полностью этот `AGENTS.md`, канонический `.codex/project-context.md`
и постоянные `work-rules.md` используемого агента:
Cursor — `.cursor/work-rules.md`, Claude Code — `.claude/work-rules.md`,
Codex — `.codex/work-rules.md`.

Проверь текущую ветку и `git status`. Сверь номер задачи и проверенную базу в контексте
с текущим checkout. После смены ветки перечитай контекст; сомнительные факты проверяй
только в непосредственно нужном коде или тестах. Текущий запрос пользователя имеет
приоритет над устаревшими записями памяти и прежними разрешениями.

Единственный файл контекста задачи для всех агентов — `.codex/project-context.md`.
Он подготовлен для этой стартовой базы и отслеживается Git. Не создавай его копии
в `.cursor/` или `.claude/` и не используй старый `.cursor/rules/project-context.mdc`
как источник состояния задачи. Существующие постоянные правила и `.cursor/rules/` сохраняй.

Если канонического контекста нет, создай компактный файл по текущему Task/Guide
и необходимым файлам этой базы. Существующий контекст сначала прочитай;
не заменяй его общим шаблоном. Это договорённость проекта, а не встроенная auto memory.

## Подключение инструкций

Cursor и Codex поддерживают корневой `AGENTS.md`; остальные указанные файлы
нужно явно прочитать по его инструкции. Произвольный Markdown в папке агента
сам по себе не означает автозагрузку. Нативные Cursor rules используют `.mdc`
и frontmatter; не заменяй их файлами `.md`.

Автоматическое чтение `AGENTS.md` в Claude Code зависит от версии и настроек.
При первом запуске или если инструкции не загрузились ученик даёт запрос:

> Прочитай корневой AGENTS.md и выполни его инструкции первичной настройки для Claude Code.

Для совместимого подключения создай локальный `.claude/CLAUDE.md` с imports:

```text
@../AGENTS.md
@../.codex/project-context.md
@work-rules.md
```

Пути считаются относительно `.claude/CLAUDE.md`. Если файл уже существует,
сохрани его содержимое и подключи недостающие imports без дублирования;
ссылку на отдельную копию контекста замени канонической. Проверь подключение
через `/context`. Не обходи подтверждения imports, если их требует агент.
Локальный адаптер не коммить. Первый запрос можно использовать и для Cursor/Codex,
если корневые инструкции не появились в новой сессии.

## Содержание канонического контекста

Держи несколько коротких разделов:

- Ветка, текущая задача и проверенный commit стартовой базы.
- Очень краткое описание проекта в состоянии этой базы.
- Уже существующие контракты и компоненты, необходимые именно текущей задаче.
- Минимальная цель, ориентиры на нужные Task/Guide, файлы и проверки.

Разделяй уже реализованное поведение и работу, которую ещё требуется сделать.
Включай факт предыдущей задачи только при понятной пользе для текущей.
Не добавляй будущие задачи, общий пересказ истории, готовую реализацию,
личные журналы, старые разрешения на commits, секреты, env-значения и длинные логи.
Не пересказывай целиком Task/Guide и не привязывай инструкции к личному каталогу автора.
Непроверенное явно обозначай.

## Постоянные правила

Существующий `work-rules.md` прочитай и сохрани. Если его нет, создай только файл
используемого агента на основе архитектурных границ ниже, существующих
`.cursor/rules/code-style.mdc` и фактических Prettier/ESLint настроек.
Не создавай сразу все три комплекта правил.

Стиль сверяй с `backend/.prettierrc.json`, `frontend/.prettierrc.json`
и соседними `eslint.config.mjs`; реальные настройки имеют приоритет над старыми советами.
Требование конкретного Task не выдавай за правило ESLint.
Не пересоздавай постоянные правила при новой задаче или commit.
Меняй их только по запросу пользователя либо при согласованном изменении lint/format.

## Архитектура и данные

- Сохраняй Controller → Service → PrismaService, Nest DI и feature modules.
  Добавляй только необходимые слои; Repository/CQRS/DDD не нужны как обёртка над Prisma.
- Проверяй входные данные на HTTP-границе и явно собирай разрешённые Prisma data.
  JWT подтверждает личность; membership и права проверяются отдельно.
  Сохраняй workspace isolation на list- и ID-endpoints.
- Изменения схемы оформляй migration; опубликованные migrations не переписывай.
  При неизменной схеме пустая migration не нужна, `db push` не заменяет migration.
- Не выводи passwords, hashes, JWT, Authorization или значения secrets.
  Проверки с записью данных выполняй только на выделенной тестовой БД.
  Не удаляй общий PostgreSQL volume и не используй `down -v` как обычный шаг.

## Перед разрешённым commit

Обнови канонический контекст только по фактам сделанных изменений и staged diff,
которые нужны для дальнейшей работы над текущей задачей. Если менялись документы,
не придумывай изменения реализации. Не превращай контекст в журнал и не пересобирай
постоянные правила.

Подготовленный `.codex/project-context.md` можно включать в commit стартовой ветки
по прямому поручению пользователя; прежний общий запрет на staging папки `.codex`
к этому файлу не относится. Личные заметки, локальные адаптеры и созданные локальные
work-rules не коммить. Уже отслеживаемые постоянные правила сохраняй.
Добавляй только явно выбранные пути, не используй `git add .` или `git add -A`.
Не меняй ignore-правила автоматически. Эта инструкция сама по себе commit не разрешает.

## Границы работы

- Работай в сохранённом checkout. Без отдельной команды не создавай worktree,
  не выполняй fetch/pull, commit/push/merge и не переписывай историю.
- Согласованные чтения, правки и проверки выполняй самостоятельно.
  Сохраняй чужие правки и не расширяй задачу на соседние документы, код,
  конфигурации или README.
- При работе над Task/Guide читай только необходимые материалы.
  Запрос редактуры не означает реализацию задания.
  Secret scan, если запрошен, ограничь этими документами без вывода значений.
- Не запускай приложение, migrations, seed, E2E или полный аудит ради обычной
  правки Markdown. Выбирай соразмерные проверки и не повторяй их без причины.
- Сообщай кратко по-русски: результат, проверки и оставшиеся ограничения.
