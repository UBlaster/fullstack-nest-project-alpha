# Правила работы с проектом

Первичная редакция основана на `.cursor/rules/code-style.mdc`, архитектуре и ограничениях
`.cursor/rules/project-context.mdc`, фактических Prettier/ESLint конфигурациях и указаниях пользователя.
Это локальный файл, не часть commits. При каждом commit он не пересоздаётся; постоянные правила
меняются только по запросу или при согласованном изменении соответствующих настроек.

## Объём и самостоятельность

- Начинай с контекста проекта и текущего запроса. Не исследуй весь репозиторий заново,
  если задача касается конкретного документа или участка кода.
- Выполняй согласованные чтения, правки и проверки самостоятельно. Не запрашивай повторно
  разрешение на уже порученную работу. Существенную неоднозначность уточняй кратко.
- Работай непосредственно в сохранённом checkout. Без отдельной команды пользователя
  не создавай worktree, не выполняй fetch/pull, commit/push/merge и не переписывай историю.
- Перед изменениями проверь branch/status и сохрани чужие правки. Не расширяй scope,
  чтобы исправить попутно найденные проблемы.
- Перед каждым разрешённым commit обновляй только `.codex/project-context.md` по сделанным
  изменениям и staged diff. Папку `.codex/` не добавляй в staging/commit; не меняй ignore-правила.
- Отчёты пиши по-русски, кратко: результат, проверки, оставшиеся ограничения.

## Работа над Task/Guide

- Редактура задания не означает реализацию задания. Меняй только указанные документы.
- Читай конкретный Task/Guide и уже имеющийся контекст. Дополнительный код/тесты читай только
  при необходимости проверить конкретный контракт или по явному запросу на аудит.
- Форматируй только разрешённые файлы; проверяй fences, Mermaid, локальные ссылки и согласованность.
- Secret scan выполняй только для редактируемого Task/Guide, если он нужен по запросу.
  Выводи файл/тип находки, не значения. Demo-пароль в учебном примере не является production secret.
- Не запускай сборку всего приложения, migrations, seed, E2E или полный secret scan ради Markdown.
- Правила `.cursor`, work-rules и AGENTS.md обновляй только когда это включено в запрос.
  Обновление project-context перед разрешённым commit уже предписано AGENTS.md.
  README, соседние задания и ignore-правила автоматически не меняй.

## Код, данные и проверки

- Стиль определяется существующими Prettier/ESLint конфигурациями; LF, табы для TypeScript,
  визуальная ширина 2, printWidth 100. Не навязывай переносы, которые formatter не сохраняет.
- Текущие настройки: semi, singleQuote, trailingComma all; Prettier интегрирован в ESLint.
  Frontend также использует react-hooks и react-refresh. no-explicit-any сейчас отключён в обоих
  ESLint-конфигах: запрет `any` в учебных HTTP-примерах — требование Task/Guide, не сообщение линтера.
- Копируемые учебные примеры имеют imports, decorators, DI wiring и типы без `any`.
- Controller делегирует service; service проверяет сценарий/доступ и явно собирает Prisma data.
- Используй Nest DI и feature modules. Не добавляй Repository/CQRS/DDD, event bus или поздние
  подсистемы без соответствующей задачи. Сохраняй tenant isolation на list- и ID-endpoints.
- Схема меняется через migration. При неизменной схеме пустая migration не нужна;
  опубликованные migrations не переписывай, `db push` не заменяет migration.
- Проверки соразмерны изменению. E2E/seed с записью данных запускай только на выделенной
  тестовой БД. Не удаляй общий PostgreSQL volume и не используй `down -v` как обычный шаг.
- Не выводи passwords, hashes, JWT, Authorization и значения env/secrets в логи или отчёт.
- Полную проверку проекта проводи только если она прямо запрошена или обоснована изменением.
  Для уже проверенных фактов используй результаты текущей сессии, не повторяй проверки без причины.
